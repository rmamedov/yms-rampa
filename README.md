# YMS «Рампа»

Yard Management System для керування прямими поставками в магазини мережі «Сільпо»: постачальник бронює слот розвантаження, водій отримує маршрутний лист і відмічає прибуття, магазин фіксує розвантаження.

Специфікація вимог (SRS, 13 розділів) — [Confluence](https://food-tech.atlassian.net/wiki/spaces/1/pages/2546434096/YMS+SRS), локальна копія — `../YMS-Rampa-SRS.md`.

## Що вже працює

Слотовий движок (`src/Domain/Slot`) — обчислення сітки слотів на льоту з конфігурації магазину, без матеріалізації слотів у БД (вимога SLOT-01). Реалізовано повністю фреймворконезалежним кодом, тому логіка тестується без БД, Redis і HTTP.

Покрито вимоги розділу 6 SRS:

- **SLOT-02** — канонічний ключ слота `(storeId, rampId, slotStart)`, без окремого `slotId`.
- **SLOT-03** — шість станів слота і пріоритет накладання: `past → blocked → booked → held → reserved → available`.
- **SLOT-04** — детермінованість: однакові вхідні дані завжди дають однакову сітку.
- **GRID-01** — порядок обчислення: вікна прийому → нарізання на слоти по кожній рампі → блокування → резерви → бронювання → холди → минуле і lead time → горизонт.
- **GRID-02** — lead time (дефолт 60 хв, 0–1440).
- **GRID-03** — горизонт бронювання (дефолт 14 днів); дата поза горизонтом кидає `DateOutOfHorizonException` (на рівні HTTP → 422 `DATE_OUT_OF_HORIZON`).
- **GRID-04** — видимість резервів: закріпленому постачальнику слот доступний із позначкою «ваш резерв», іншим — недоступний і **без розкриття**, за ким закріплено.
- **GRID-05** — сітка віддає `maxVehicleWeightTons`, `slotSizeMinutes`, `leadTimeMinutes` і серверний `now`.
- **GRID-06** — критерій приймання (вікно 08:00–14:00, слот 30 хв, 2 рампи = 24 слоти; блокування рампи на 2 години прибирає рівно 4) закріплений тестом.

Окремо оброблено крайові випадки, яких немає в наївній реалізації: перехід на літній час (локальної 03:00 в ніч переведення не існує — слот не породжується), повернення з літнього часу (сітка лишається детермінованою), неповний «хвіст» вікна прийому, кілька інтервалів прийому на день, вимкнені рампи, календарні винятки (свято/інвентаризація/скорочений день), разові та щотижневі резерви з періодом дії.

## Запуск

Вимоги: PHP 8.3+, Composer. БД поки не потрібна.

```bash
cd services/booking-service && composer install
```

Тести:

```bash
cd services/booking-service && vendor/bin/phpunit
```

Наочний перегляд сітки слотів:

```bash
cd services/booking-service && php bin/console yms:slots:preview --date=2026-09-07 --block=ramp-2:10:00-12:00 --reserve=supplier-critical:ramp-1:09:00 --supplier=supplier-a
```

## Структура

```
services/          мікросервіси Symfony (поки лише booking-service)
apps/              Angular-застосунки: admin-web, store-web, supplier-web, driver-web
fixtures/          довідник філій з MCP Сільпо та похідні дані
infra/             локальне оточення і деплой
docs/              проєктна документація
```

## Технологічний стек

Зафіксований специфікацією: PHP 8.3+ / **Symfony 7.4 LTS**, MongoDB 7.x, Angular 18+, RabbitMQ (Symfony Messenger), Redis, Kubernetes.

## Наступні кроки

1. Персистентність booking-service: MongoDB, частковий унікальний індекс на `(storeId, rampId, slotStart)` серед активних статусів (BOOK-07) і сценарій гонки двох постачальників (BOOK-08).
2. Холди слотів у Redis: `SET NX` з TTL 5 хв і продовженням при активності до 15 хв (HOLD-01…04).
3. `store-service`: імпорт філій з `fixtures/silpo-branches.json` з фільтрацією сміттєвих записів (див. `fixtures/README.md`) і CRUD конфігурацій магазинів.
4. HTTP API booking-service: `GET /stores/{storeId}/slots`, `POST /slots/hold`, `POST /bookings`.
5. Два контури автентифікації і RBAC.
6. Angular-застосунки, починаючи з `supplier-web`.

Локальна інфраструктура: Redis встановлено. MongoDB потребує довіри до тапа Homebrew — команду має виконати розробник:

```bash
brew trust --formula mongodb/brew/mongodb-community && brew install mongodb-community
```
